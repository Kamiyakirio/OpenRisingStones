# 游戏聊天手机桥接设计

## 1. 目标

为 Windows 桌面端增加一个由用户显式开启的游戏聊天桥接功能：

- 读取已经到达并被游戏客户端聊天系统处理的消息；
- 在桌面端查看连接状态、局域网地址和最近消息；
- 生成一次性配对二维码，让同一可信局域网中的手机打开聊天页面；
- 从手机提交文本，并在游戏 Framework 主线程调用原生聊天入口发送；
- 关闭功能、退出应用、游戏断开或会话过期后立即停止访问。

第一版只支持可信局域网，不提供公网中继、端口映射、自动回复、定时发送或无人值守发送。

## 2. 风险确认

本功能复用现有 `RiskDialog` 风险 wall。首次启用前必须明确提示：

- 功能会向游戏进程加载桥接模块并读取聊天内容；
- 手机发送会调用游戏原生聊天处理函数，属于影响游戏操作的第三方程序行为；
- 国服用户协议把运行时影响游戏操作、模拟输入、逆向和修改 RAM 等行为列入禁止范围；
- 使用者需自行承担账号处罚、客户端崩溃和聊天隐私泄露风险；
- 局域网 HTTP 为明文通信，只应在可信家庭网络中使用。

用户确认状态沿用现有本地确认记录模式。确认只表示用户理解风险，不改变运营方规则，也不构成安全保证。版本更新、风险文案版本变化或本地记录不可用时应重新确认。

## 3. 技术边界

### 3.1 读取聊天

Payload Hook `RaptureLogModule::PrintMessage`，在调用原函数前复制以下有界数据：

- 单调递增序号；
- `LogKind` 频道编号；
- source/target relation；
- 游戏时间戳；
- sender 的原始 SeString 字节；
- message 的原始 SeString 字节。

Hook 不执行 JSON、HTTP、磁盘写入或动态业务逻辑，只把有界消息写入共享内存中的单生产者/单消费者环形缓冲区，然后立即调用原函数。环形缓冲区满时覆盖最旧消息并增加 dropped 计数，绝不阻塞游戏线程。

Host 消费消息后解析 SeString。第一版只输出安全纯文本和基础元数据；未知 payload 被忽略，不把控制字节直接插入 HTML。网页始终按文本节点渲染。

“全部聊天”定义为桥接启动后，已经到达并进入客户端 `RaptureLogModule` 的消息。服务端未发送、客户端在更早阶段丢弃、桥接启动前已过期或被其他插件拦截的消息不在保证范围。初次连接可读取客户端现有日志缓存中的最近消息，但读取失败不得阻止后续实时消息。

### 3.2 发送聊天

2026-09-20 的首次实机发送暴露了一个原生参数组合错误：Payload 调用了
`ProcessChatBoxEntry(uiModule, message, 0, true)`。游戏反汇编显示，`saveToHistory=true`
时会进入输入历史分支，并把第三个参数当作另一个原生字符串来源拷贝；空指针最终在
`ffxiv_dx11.exe+88DDB` 的 `[rdx+0x10]` 解引用处崩溃。修复后的调用固定为
`ProcessChatBoxEntry(uiModule, message, 0, false)`，与公开结构声明的默认参数一致，
不会进入要求非空 history context 的分支。不得在 context 为空时重新启用历史保存。

以下为发送必须满足的设计约束：

手机文本经过 HTTP 层和 Host 校验后，转换为固定语义 `SendChat` 命令。Payload 只在 Framework Tick 中执行：

1. 验证游戏处于可发送状态；
2. 验证消息为合法 UTF-8、非空且不超过协议上限；
3. 使用游戏原生 `Utf8String::Ctor` 构造临时字符串；
4. 使用 `Utf8String::SetString` 写入文本；
5. 调用 `UIModule::ProcessChatBoxEntry`；
6. 使用 `Utf8String::Dtor` 清理临时字符串；
7. 向 Host 返回固定状态码。

不得把普通 `char*` 直接伪装成 `Utf8String`，不得在 HTTP 线程调用游戏函数，也不得构造或发送游戏网络包。

第一版发送策略：

- 默认把纯文本发送到游戏当前活动聊天频道；
- 公开手机接口拒绝以 `/` 开头的任意命令；
- 内部测试可以使用受编译条件保护的 `/echo` 诊断；
- 桌面端和手机端共同执行长度限制与限流，Payload 再做最终校验；
- 游戏不在世界中、正在过图、断线或 Payload 未就绪时拒绝发送。

## 4. 共享内存协议

共享内存 ABI 升级一个主版本，并增加：

- `SendChat` 命令与固定长度 UTF-8 输入区；
- 固定容量聊天事件环形缓冲区；
- `chatWriteSequence`、`chatReadSequence` 和 `chatDroppedCount`；
- 每条消息独立长度字段，禁止依赖未终止字符串；
- 聊天 hook 和原生字符串函数的受验证地址。

Host 仍然不接受任意地址、任意内存写入或任意函数调用。Manifest 必须继续满足精确游戏版本、`.text` SHA-256、唯一 AOB 匹配和模块范围校验。缺少任一聊天签名时，聊天桥接显示为“不支持当前游戏版本”，其他桥接功能保持可用。

## 5. 局域网 HTTP 服务

HTTP 服务运行在 Tauri/Rust 进程，不运行在注入 DLL 中。用户点击开启后：

1. 选择可用的私有 IPv4 地址；
2. 在随机高位端口监听；
3. 生成 256 bit 随机配对密钥和短期会话；
4. 二维码只携带页面地址和 URL fragment 中的一次性密钥；
5. 手机 JavaScript 从 fragment 读取密钥并调用 `/api/pair`；
6. 服务端验证后设置短期、`HttpOnly`、`SameSite=Strict` 会话 Cookie；
7. fragment 随即从浏览器地址栏移除。

手机页面使用仓库现有的 React、TypeScript 和 Vite 工具链，并使用独立的 `mobile.html` 入口：

- Debug 构建由 Vite 在局域网地址提供页面和 React Fast Refresh；`/api` 与 SSE 请求代理到只监听 `127.0.0.1:1421` 的 Rust 服务，因此调试接口不会直接暴露到局域网；
- Release 构建输出标准的多文件 Vite 产物，保留带 hash 的 JavaScript 与 CSS；Rust 使用 `rust-embed` 嵌入整个产物目录，并通过 Axum 与 `mime_guess` 按原始路径和 MIME 类型提供；
- Debug 与 Release 共用同一套 React 组件和 Rust API，不维护第二套原生 JavaScript 页面；
- Release 不使用 single-file 内联构建，确保严格 CSP 可以继续使用 `script-src 'self'` 和 `style-src 'self'`，也保留标准资源缓存与调试能力。

接口：

- `GET /`：移动端静态页面；
- `POST /api/pair`：一次性配对；
- `GET /api/state`：连接状态与初始消息；
- `GET /api/events`：SSE 消息和状态流；
- `POST /api/messages`：提交一条聊天文本；
- `POST /api/disconnect`：手机主动断开。

所有响应设置 `Cache-Control: no-store` 和严格 CSP。服务端验证 Host、Origin、会话 Cookie、请求体大小和 Content-Type。配对失败和发送失败使用稳定英文错误码；面向用户的页面文案使用中文。

第一版跟随系统默认路由选择私有 IPv4 地址，不启用 UPnP，不在磁盘保存聊天正文或密钥。如果默认路由指向 VPN 或虚拟网卡，手机可能无法访问；桌面端提示用户检查同一 Wi-Fi、VPN 和 Windows 防火墙。

## 6. 限流与隐私

- 单设备配对；已有设备保持会话期间拒绝新设备，切换设备需要停止并重新开启服务；
- 配对密钥只能成功使用一次，默认五分钟过期；
- 会话最多持续两小时，桌面端关闭服务时立即失效；
- 发送至少间隔一秒，并设置分钟窗口上限；
- 内存只保留最近 500 条安全文本消息；
- 日志不得记录配对密钥、Cookie 或聊天正文；
- 手机页面后台时不弹出系统通知；
- 第一版转发捕获到的全部聊天频道；风险 wall 明确提示私聊、部队和通讯贝等内容会暴露给已配对手机。

## 7. UI

桌面端增加“手机聊天”工作区，沿用当前应用的暖色任务台设计：

- 未确认风险：只显示功能说明和开启动作，点击后进入现有风险 wall；
- 未运行：显示游戏连接条件和“开启手机聊天”；
- 启动中：显示真实阶段，不提前展示二维码；
- 已运行：左侧显示最近消息，右侧显示二维码、局域网地址、配对状态和停止按钮；
- 不支持版本：说明需要重新采集 Manifest；
- 网络不可达：说明检查同一 Wi-Fi 和 Windows 防火墙；
- 手机端：消息流占据主体，底部固定输入区，发送中禁止重复提交。

桌面页面是控制台，不把聊天内容设计成宣传卡片。移动页面优先保证单手发送、软键盘避让、断线恢复、可见焦点和 44px 以上触控目标。

## 8. 失败与卸载

- Hook 安装失败：禁用聊天功能，不使现有桥接进入不可恢复状态；
- 原生调用失败：返回稳定错误，保持服务运行，由用户重试；
- 游戏退出或 Payload 心跳停止：停止发送并向手机发布离线状态；
- Payload 卸载：先停止新命令，再关闭聊天 hook，等待活动回调归零，最后移除 Framework hook；
- 应用退出：停止 HTTP listener，清除会话与消息内存，再关闭游戏桥接。

## 9. 验收顺序

1. ABI、Manifest 和环形缓冲区单元测试；
2. 测试账号只读验证：中文、时间戳、频道、SeString、过图和角色切换；
3. 使用内部 `/echo` 验证 `Utf8String` 生命周期与主线程调用；
4. 经同意后验证小队频道发送；
5. 验证手机配对、过期、限流、重复提交和停止服务；
6. 验证 Windows 防火墙、多个网卡、断网和游戏退出；
7. 桌面 1440px 与移动 390px 视觉和键盘可用性检查。

无法在没有目标游戏二进制和测试账号的环境中替代第 2 至第 6 项真实验证。未通过真实验证的构建必须明确标记为实验性，不能宣称支持当前游戏版本。
